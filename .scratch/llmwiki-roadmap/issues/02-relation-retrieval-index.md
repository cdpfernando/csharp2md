# 02 — Relation retrieval index & sharding

**Feature slug:** `relation-retrieval-index` (`.specs/features/relation-retrieval-index/` once Specify starts)
**Roadmap row:** §9 P0 "Índice de recuperação do gerador"
**Fase (tlc-spec-driven):** Implemented
**Execução:** agnóstica de agente/LLM — processo lido de `.agents/skills/tlc-spec-driven/` (espelhado, hash
idêntico, em `.claude/`/`.cursor/`/`.windsurf/`); não depende de skill nativa de uma ferramenta específica.
Ver roadmap § "Estado do documento".

**What to build:** The roadmap's own "next milestone" line: a derived, versioned, regenerable retrieval-index
layer over the already-persisted factual fragments — explicitly not a second source of truth, not a rewrite
of `raw/facts`, and not a wiki page. The real validation run in `llmwiki-reverse-engineering-roadmap.md`
Appendix A produced roughly 1.0 GiB of raw relations and a 642 MiB `structural.json` projection across
206,484 relations, 72.7% of them unresolved — nothing downstream can load that as LLM context today. This
ticket builds the layer that makes it retrievable:

- shards by project, source id, target id, relation kind, and resolution state, each with a predictable
  size ceiling
- a per-project/per-category count summary
- an index of entry points, integrations, events, entities, and high-centrality relations
- UNKNOWNs grouped by cause, source, and target text — never one row per unresolved relation (150k+ in the
  observed run)
- `analysis.effective`, `trust`, and `restore_performed` propagated into the index/summary output, so a
  consumer can tell that zero DI/gRPC/compile-time relations in a `syntax-only` run means "not analyzed,"
  never "absent from the system"
- the `resolution` (proof quality) vs `resolution_method` (route taken) distinction from Appendix A.2
  formalized in `schemas/facts.schema.json` or equivalent consumer-facing schema docs, so the two fields
  can't be silently conflated by a future change
- a per-run quality-metrics summary (resolved/dynamic/unresolved percentage by kind/partition), comparable
  across runs

Folded in from §10 "Melhorias sugeridas" of the roadmap (immediate + precision + continuous-operation
items, mapped 2026-08-22 — each is a consumer-safety or observability concern for this exact layer, not
separate work):

- `schemaVersion` and `analysisRunId` on the index/relation output, so the analyzer and a downstream
  consumer can never silently disagree about shape or which run produced a shard
- verification that no persisted relation id is generated non-deterministically end to end (the id grammar
  already guarantees this per AD-014/`RelationFactId.Create` — this is a proof against real output, not new
  identity logic)
- complete provenance per evidence entry: repo/analysis version, project, document, content hash
- the serializer's dedup rule collapses only relations that are semantically identical with compatible
  evidence — a distinct location or context that changes meaning must survive as a distinct entry
- new fields are additive and unknown fields are preserved through the index, never dropped
- the UNKNOWN queue is ordered by impact (entry points and high-centrality relations first), not just
  grouped by cause
- facts/evidence carry a generated-code origin marker (e.g. from `<auto-generated>` headers or known
  generator tooling), even though *using* that marker to discount architectural inferences is wiki-ingestion
  scope and stays out of this ticket
- the per-run summary also reports indexed-symbol counts and mapped-entry-point counts alongside the
  resolved/dynamic/unresolved proportions already listed above ("valid links" stays out — that is a wiki-page
  concern, not this generator's)

**Blocked by:** None — reads the same persisted fragments as everything else; the roadmap explicitly notes
this can proceed in parallel with the component-graph work.
