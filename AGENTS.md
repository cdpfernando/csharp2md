# csharp2md

## Working principles

1. **Think first.** Inspect the relevant code and documentation before editing. State important assumptions and never guess Roslyn APIs.
2. **Keep it simple.** Implement only what the user asked for. Avoid speculative features, abstractions, and configuration.
3. **Make surgical changes.** Follow existing patterns, preserve unrelated work, and keep every changed line traceable to the request.
4. **Verify the goal.** Define a concrete success check, run the relevant tests or build, and report anything that could not be verified.

## Project rules

- Product semantics are normative in `CONTEXT.md` (domain language), `.specs/STATE.md` `## Decisions`, `docs/specs/pacote-conhecimento-util-e-confiavel.md` and its feature under `.specs/features/pacote-conhecimento-util-e-confiavel/`, in that order. Where the code diverges from them, the divergence is a defect.
- Spec-driven work lives in `.specs/features/`. Create a new feature only when the user explicitly starts that work. Execute it with the `tlc-spec-driven` skill, activated by name.
- Do not load or recreate superseded specs, tickets, ADR prose, relation taxonomies, CLI contracts or output schemas from Git history unless the user explicitly requests historical analysis.
- The generator owns factual production and directly navigable retrieval projections. Query engines, `kb`, QMD, embeddings, wiki compilation and business-rule interpretation are deferred downstream concerns.
- `tlc-spec-driven`'s discrimination sensor (the mutation-testing step inside Execute/Validate) is a standing **skip** for this project, overriding the skill's own "never optional, never prompted" default. The user runs Stryker manually and does not want the sensor's fault-injection pass run by the agent. Do not re-ask or re-decide per feature: note the skip in the new feature's `tasks.md` header with the phrasing already used in `.specs/features/pacote-conhecimento-util-e-confiavel/tasks.md` ("**Project override:** the discrimination sensor is skipped by standing project rule; …") and move on. Every other Verifier step (spec-anchored coverage check, gate check, code-quality check) still runs as documented.
- Target framework is `net10.0`; Roslyn is `Microsoft.CodeAnalysis.Workspaces.MSBuild` 5.6.0. Do **not** reference `Microsoft.Build.*` and do **not** call `MSBuildLocator.RegisterDefaults()`: Roslyn 4.9+ loads projects through an out-of-process BuildHost.
- **Four analysis fixtures are versioned:**
  - `fixtures/SyntheticSolution` is the fast, focused one: small, hand-authored scenarios with a hand-written oracle (`knowledge-oracle.json`), cheap enough for unit and integration cases in both test projects. See its `README.md`.
  - `fixtures/ArchitectureDependencyLab` is the accuracy instrument: six `.slnx` solutions, 41 projects and a normative oracle (`oracle/project-references.json`, 87 `ProjectReference`; `oracle/scenarios.json`, 63 scenarios). It exists because a two-entity fixture cannot tell a correct graph from a complete one. It analyses cold (no restore, no build; its private packages are vendored under `local-feed/`), its `bin`/`obj` are gitignored, and it stays outside `csharp2md.slnx`. Its consumers are the `Category=OracleCorpus` cases in `Csharp2Md.Cli.Tests`, which score `project-references.json` per solution; `scenarios.json` has no test consumer.
  - `fixtures/CertificationCorpus` is the labelled precision corpus: four `labels/*.json` answer keys (entry points, contracts, linked calls, persistence) whose 17 entries mark each C# shape `positive`, `lookalike` or `negative` with an `expected` of `present` or `absent`, alongside malformed `appsettings.*.json` (BOM, comments, duplicate key, trailing comma, unterminated) and binary/web assets (`.png`, `.pfx`, `.zip`, `.js.map`) the reader has to survive. It has no test consumer.
  - `fixtures/PublicationResilience` is the deliberately unlabelled stressor: awkward signatures (named tuples, nested generics, multidimensional arrays, an invocation-only builder constructor) plus twelve bulk `Volume/DelegateVolume*.cs` files, i.e. shapes and volume the publication path must not choke on. It has no test consumer.
  - `CertificationCorpus` and `PublicationResilience` lost their last consumer in T45, so they are committed inputs with no gate watching them today; re-point or delete them deliberately rather than assuming a test covers them.
- Never commit `fixtures/eShop`, `fixtures/eShopOnContainers` or `fixtures/Pitstop` (gitignored local clones). `LocalCorpus.SolutionPath` expects them at `fixtures/eShop/eShop.slnx`, `fixtures/eShopOnContainers/eShopOnContainers-ServicesAndWebApps.sln` and `fixtures/Pitstop/pitstop.sln`. After each feature Verifier, if any clone is present, run `dotnet test tests/Csharp2Md.Cli.Tests/Csharp2Md.Cli.Tests.csproj -c Release --filter "Category=LocalCorpus"`; a case whose clone is absent skips by name. Do not fail CI for a missing local clone.
