# csharp2md

## Working principles

1. **Think first.** Inspect the relevant code and documentation before editing. State important assumptions and never guess Roslyn APIs.
2. **Keep it simple.** Implement only what the user asked for. Avoid speculative features, abstractions, and configuration.
3. **Make surgical changes.** Follow existing patterns, preserve unrelated work, and keep every changed line traceable to the request.
4. **Verify the goal.** Define a concrete success check, run the relevant tests or build, and report anything that could not be verified.

## Project rules

- The target architecture is normative in `CONTEXT.md`, `docs/architecture/`, `.specs/STATE.md`, and `architecture-knowledge-engine-roadmap.md`, in that order. Existing source and schemas are legacy implementation, not a source for future product semantics.
- Spec-driven work lives in `.specs/features/`, but no replacement feature spec exists yet. Create a feature only when its roadmap workstream is explicitly started. Execute it through `.agents/skills/tlc-spec-driven/SKILL.md` and its referenced files/scripts.
- Do not load or recreate superseded specs, tickets, ADR prose, relation taxonomies, CLI contracts or output schemas from Git history unless the user explicitly requests historical analysis. The roadmap's compact disposition table is the only legacy mapping in the working tree.
- The generator owns factual production and directly navigable retrieval projections. Query engines, `kb`, QMD, embeddings, wiki compilation and business-rule interpretation are deferred downstream concerns.
- `tlc-spec-driven`'s discrimination sensor (the mutation-testing step inside Execute/Validate) is a standing **skip** for this project, overriding the skill's own "never optional, never prompted" default. The user runs Stryker manually and does not want the sensor's fault-injection pass run by the agent. Every feature done so far (`knowledge-taxonomy-contract` through `components-deployments-configuration`) has skipped it; do not re-ask or re-decide per feature — note the skip in the new feature's `tasks.md` header (same phrasing as the prior features) and move on. Every other Verifier step (spec-anchored coverage check, gate check, code-quality check) still runs as documented.
- Target framework is `net10.0`; Roslyn is `Microsoft.CodeAnalysis.Workspaces.MSBuild` 5.6.0. Do **not** reference `Microsoft.Build.*` and do **not** call `MSBuildLocator.RegisterDefaults()` — 4.9+ loads projects via an out-of-process BuildHost (AD-003).
- **Four analysis fixtures are versioned.** `fixtures/SyntheticSolution` is the fast, focused one: small, hand-authored scenarios with a hand-written oracle, cheap enough for unit and integration cases. `fixtures/ArchitectureDependencyLab` is the accuracy instrument: six `.slnx` solutions, 41 projects and a normative oracle (`oracle/project-references.json`, 87 `ProjectReference`; `oracle/scenarios.json`, 63 scenarios) that dependency claims are scored against per solution — it exists because a two-entity fixture cannot tell a correct graph from a complete one. It analyses cold (no restore, no build; its private packages are vendored under `local-feed/`), its `bin`/`obj` are gitignored, and it stays outside `csharp2md.slnx`. `fixtures/CertificationCorpus` is the labelled precision corpus: four `labels/*.json` answer keys (entry points, contracts, linked calls, persistence) whose 17 entries mark each C# shape `positive`, `lookalike` or `negative` with an `expected` of `present` or `absent`, alongside malformed `appsettings.*.json` (BOM, comments, duplicate key, trailing comma, unterminated) and binary/web assets (`.png`, `.pfx`, `.zip`, `.js.map`) the reader has to survive. `fixtures/PublicationResilience` is the deliberately unlabelled stressor: awkward signatures (named tuples, nested generics, multidimensional arrays, an invocation-only builder constructor) plus twelve bulk `Volume/DelegateVolume*.cs` files, i.e. shapes and volume the publication path must not choke on. **Neither `CertificationCorpus` nor `PublicationResilience` has a test consumer in the current tree** — T45 cut the last one — so they are committed inputs with no gate watching them today; re-point or delete them deliberately rather than assuming a test covers them. Never commit `fixtures/eShop`, `fixtures/eShopOnContainers` or `fixtures/Pitstop` (gitignored local clones). After each feature Verifier, if those clones are present, run the `LocalCorpus` tests or the matching CLI launch profiles; skip when they are absent. Do not fail CI for a missing local clone.
